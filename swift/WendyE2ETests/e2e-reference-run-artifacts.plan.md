# Plan: Incorporate E2E reference pages into run artifacts

## Goal

Make the generated Wendy Swift E2E behavioral reference available from each
aggregated run directory and linked from the HTML report, while keeping the
existing standalone `swift-e2e-testing reference` command intact.

The run directory should remain self-contained: downloading or publishing a run
artifact should include both the execution report and the behavioral reference
that corresponds to the specs used for that run.

## Current state

- `swift-e2e-testing reference` already generates reference documentation from
  Swift E2E test sources.
- With HTML output, it writes one HTML file per Swift test source file plus an
  index.
- The E2E test organization convention is one flattened suite per test file, so
  those files are effectively one reference page per suite.
- `swift-e2e-testing aggregate` builds the canonical run layout from attempt
  directories:

  ```text
  <run>/
    <suite-key>/
      <test-key>/
        <target>/
          <attempt>/
            attempt.json
            recording.md
            recording.sh.txt
            test-results.xml
  ```

- `swift-e2e-testing report` renders `<run>/index.html` from the run layout.
  It already has a card/heading per suite.

## Decision

Keep `reference` as the standalone source-to-docs command, but have the
`aggregate` step incorporate reference pages into the run layout.

`report` should not generate reference artifacts. It should only link to them
when they already exist. This keeps the report renderer as a view over the run
artifact instead of another producer that mutates the run directory.

## Proposed run layout

Place suite references inside the corresponding suite directory and add a
root-level reference index:

```text
<run>/
  index.html                  # generated by report
  reference.html              # generated by aggregate; links to suite refs
  review.md
  review.html
  <suite-key>/
    reference.html            # generated by aggregate; suite reference
    <test-key>/
      <target>/
        <attempt>/
          ...
```

Example:

```text
<run>/
  reference.html
  wendy-device-info/
    reference.html
    prints-json-device-information/
      macos-15-to-wendyos-raspberry-pi-5/
        0001/
          recording.md
```

## Aggregate behavior

Add reference aggregation to `swift-e2e-testing aggregate` after attempts are
mapped into run directories.

Suggested options:

- Add `--package-dir`, defaulting to the current package when invoked from
  `swift/WendyE2ETests` or to the existing script-provided package path.
- Add `--tests-dir`, defaulting to `Tests/WendyE2ETests` under the package.

For each generated run directory:

1. Discover suites that are present in the run directory.
2. Match each suite key to its Swift test source file using the same suite-key
   derivation already used by report/review (`recordFileStem` / slugged test
   file stem).
3. Parse the matching Swift source with `WendyE2EReference.parseFile`.
4. Write suite HTML to:

   ```text
   <run>/<suite-key>/reference.html
   ```

5. Write root reference index to:

   ```text
   <run>/reference.html
   ```

   with links to each `<suite-key>/reference.html`.

Only generate suite references for suites present in the aggregated run. This
avoids creating suite directories just because a test source file exists.

## Reuse and extraction

The standalone `reference` command should continue to work as-is. To avoid
copying logic:

- Extract shared helpers for:
  - discovering Swift reference source files,
  - deriving reference output names/links,
  - writing a set of reference documents and an index.
- Keep `ReferenceCommand` as the CLI entry point for explicit reference
  generation.
- Let `AggregateCommand` call the shared helper with a run-aware destination
  layout.

The existing `reference` command can keep its current `--output` behavior,
including one generated file per suite and an index file, independent of the
run-specific layout.

## Report behavior

Update `swift-e2e-testing report` to render links only when the reference files
exist.

Top-level header:

```html
Run ID: <code>...</code> · Reference: <a href="reference.html">HTML</a>
```

Suite card heading:

```html
<div class="card-title">
  <h2>Wendy Device Info</h2>
  <a class="report-button" href="wendy-device-info/reference.html">Reference</a>
</div>
```

Implementation notes:

- Add a `{{REFERENCE_LINK}}` placeholder beside `{{REVIEW_AGGREGATE_LINK}}` in
  `Support/e2e-report.template.html`.
- Add `renderReferenceLink(runURL:)` for the run-level link.
- Add suite-level link rendering in `renderCards(files:)`, using
  `<suite-key>/reference.html` when that file exists.
- Keep links relative so the run directory can be opened directly from disk or
  hosted as static artifacts.

## Script integration

Update the aggregate wrappers, not the report wrappers, to pass the test source
location when needed:

- `swift/Scripts/E2EAggregate.sh`
- `swift/Scripts/E2EAggregate.ps1`
- any analyze path that invokes aggregate indirectly

`E2EReport.sh` / `E2EReport.ps1` should continue to render only the report.
They should not invoke `reference` or mutate the run with reference artifacts.

## Compatibility and cleanup

- Existing run directories without reference artifacts should still render
  reports successfully; the report simply omits reference links.
- Re-running aggregate for a run should overwrite stale suite `reference.html`
  files and the root `reference.html`.
- If a suite no longer exists in the run, aggregate should avoid leaving stale
  root index entries. Ideally it should rewrite the root reference index from
  current run contents.
- Avoid naming the root index `index.html` to prevent colliding with the report.

## Tests to add

- Unit-level coverage for the run-reference writer:
  - writes `<run>/reference.html`,
  - writes `<run>/<suite-key>/reference.html`,
  - includes only suites present in the run layout,
  - produces relative links.
- Report rendering coverage or snapshot-style assertions for:
  - top-level reference link present when `<run>/reference.html` exists,
  - suite reference link present when `<run>/<suite-key>/reference.html` exists,
  - links omitted when files are absent.
- Smoke test:

  ```sh
  cd swift/WendyE2ETests
  swift test --filter WendyE2ETestingTests
  ```

## Open questions

- Should aggregate fail if reference generation fails, or warn and continue?
  The initial preference is to fail, because a malformed spec should be visible
  when producing a canonical run artifact.
- Should a future report expose direct reference anchors per test? The first
  version should keep only suite-level links to minimize report complexity.
