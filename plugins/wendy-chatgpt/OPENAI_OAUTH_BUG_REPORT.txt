Subject: Plugin portal requires a missing OAuth client ID with both explicit and discovered client configuration

The OpenAI plugin submission portal blocks our Wendy MCP connection with:

"MCP details save failed: OAuth client ID is required when using pre-defined
OAuth client credentials."

With package 0.5.4, captured validation received client_id=undefined even though
the connection drawer's JSON displayed the client ID. A subsequent package
candidate omitted the optional auth.client object; the user supplied a screenshot
showing that configuration loaded and the same missing-client-ID error.
This blocks OAuth connection and tool discovery for our existing Wendy draft,
leaving MCP setup incomplete and preventing submission.
Please route this to the team responsible for the plugin submission portal's
MCP connection form.

Latest result: omitted-client candidate, 2026-10-17

We prepared wendyos-0.5.5-oauth-discovery.zip, removing only auth.client and
updating the package version and release notes. The user then reported the same
failure and supplied a screenshot of the Wendy connection drawer showing:

{
  "type": "oauth",
  "baseScopes": ["mcp:relay"],
  "defaultScopes": [],
  "oidcEnabled": false
}

The screenshot displays the unchanged missing-client-ID error, MCP key
wendy-relay, endpoint https://mcp.wendy.dev, domain verified, and authorization
required. The optional-client omission is visibly present, so this package
experiment did not resolve the failure. The screenshot does not show the package
version or internal saved state. We did not capture new network or breakpoint
evidence for this attempt; the detailed runtime observations below apply to 0.5.4.

OpenAI's documented schema permits omitting auth.client:
https://developers.openai.com/plugins/build/plugins#oauth-configuration-reference

Please repair or provide a supported way to reset the existing draft's OAuth
configuration while preserving its plugin identity and review materials. Please
check why the connection form requires predefined-client credentials when the
displayed package no longer selects a predefined client. A successful OAuth
connection and tool scan remain unverified.

Possible area to investigate

The public portal code displays settingsJson separately from form values loaded
from app/version data. It also contains a mode-resolution effect and a discovery
refresh guard conditioned on saved use_cimd/client_id values. These may explain
the inconsistent state, but their execution order was not traced. This is a
hypothesis, not a confirmed initialization race.
