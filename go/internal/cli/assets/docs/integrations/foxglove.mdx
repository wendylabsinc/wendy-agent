Wendy for Foxglove turns a device's live ROS 2 graph into something you can *see*
and *drive*. The CLI hosts a [Foxglove WebSocket Protocol](https://foxglove.dev/)
server on your machine and bridges it to the device's ROS 2 system, so you can
drop a Raw Message panel, plot a signal, watch a camera feed, set a parameter,
call a service, or publish a command — without installing anything on the device.

## How it works

The server runs on your machine (default `127.0.0.1:8765`) and reaches the
device's ROS 2 system over the existing mutually-authenticated gRPC connection.
Your data never leaves your machine to a third party.

```
Foxglove Studio ──ws──► wendy CLI (host) ──gRPC (mTLS)──► wendy-agent ──exec──► ros2 sidecar
 (foxglove.websocket.v1)  foxglove server      ROS2Service          ros2 / rclpy (shares app DDS domain)
```

The CLI discovers the device's ROS 2 topics, advertises them to Foxglove with the
right encoding and schema, and forwards messages as they arrive — building on the
same sidecar mechanism as [Wendy for ROS 2](/docs/integrations/ros2).

### Efficient for large messages

The subscribe path is built for high-bandwidth topics — uncompressed camera
frames, point clouds, lidar scans. On the device, a small `rclpy` forwarder
raw-subscribes each topic and streams the serialized **CDR bytes straight
through**, framed in binary. There is no text encoding and no per-message decode
on the device, and messages are forwarded to Foxglove exactly as DDS produced
them (`encoding: cdr`). Large messages that a naïve bridge would drop or inflate
flow intact.

## Usage

Start the bridge against your default device:

```bash
wendy device foxglove serve
```

Then, in Foxglove Studio (desktop or [app.foxglove.dev](https://app.foxglove.dev)),
choose **Open connection** and enter:

```
ws://localhost:8765
```

Discovered topics appear as channels you can add to any panel. New topics are
advertised (and vanished ones removed) automatically on the `--poll` interval.

### Read-only by default; opt in to control

By default the bridge is **read-only**: you can subscribe to topics and read
parameters, but Foxglove cannot change anything on the device. To let Foxglove
**command the device** — publish to topics, call services, and set parameters —
start with `--allow-control`:

```bash
wendy device foxglove serve --allow-control
```

<Callout type="warning">
`--allow-control` lets Foxglove write to a live robot: publishing to a topic or
calling a service can move actuators. Only enable it when you intend to control
the device.
</Callout>

### Flags

| Flag | Description |
| --- | --- |
| `--port` | WebSocket listen port (default `8765`). |
| `--host` | Bind address (default `127.0.0.1`). |
| `--domain` | `ROS_DOMAIN_ID` override (default: from the app's ROS 2 config). |
| `--topic` | Restrict to specific topics; repeatable. Defaults to all topics. |
| `--poll` | Topic re-discovery interval (default `5s`; `0` disables). |
| `--allow-control` | Enable the write path — publish, service calls, set parameters (default: read-only). |

## What you can do

- **Visualize** — subscribe to any topic; raw messages, plots, images, 3D, and
  the full Foxglove panel set work against the device's live data.
- **Parameters** — read every node's parameters; with `--allow-control`, set them
  from Foxglove's Parameters panel. (Foxglove names parameters `<node>:<param>`.)
- **Services** *(`--allow-control`)* — advertised services can be called from
  Foxglove's Service Call panel; the request/response are bridged to
  `ros2 service call`.
- **Publish** *(`--allow-control`)* — publish to a topic from Foxglove; each
  message is bridged to `ros2 topic pub`.
