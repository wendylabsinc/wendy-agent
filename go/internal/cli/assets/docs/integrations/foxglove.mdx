title: Wendy for Foxglove
description: Stream a WendyOS device's live ROS 2 topics into Foxglove Studio for real-time visualization, with a single command and nothing to install on the device by hand.
---

Wendy for Foxglove turns a device's live ROS 2 graph into something you can *see*.
One command deploys the standard `foxglove_bridge` node to the device, joins it to
the device's ROS 2 graph, and forwards its WebSocket port to your machine. Wendy
exposes a bandwidth-safe set of transforms, odometry, diagnostics, and compressed
camera topics by default; opt in to other topics when you need them.

```bash
wendy device foxglove serve
```

This form deploys to the selected LAN device and forwards the port directly over
the LAN. To deploy to a cloud-connected device instead, use:

```bash
wendy cloud device foxglove serve --device <id-or-name>
```

Then, in Foxglove Studio (desktop or [app.foxglove.dev](https://app.foxglove.dev)),
choose **Open connection** and enter:

```
ws://localhost:8765
```

Discovered topics appear as channels you can add to any panel.

## How it works

`wendy device foxglove serve` runs three steps for you:

1. **Generates a bridge app.** The CLI writes a temporary app: a Dockerfile based
   on `ros:<distro>` with the distro's `foxglove_bridge` package installed, and a
   `wendy.json` with a `frameworks.ros2` block (your `--domain`, `--rmw`, and
   `--distro`), host-scoped DDS discovery, and a host-network entitlement. This
   lets the bridge join the device's whole ROS 2 graph, including a robot's native
   host ROS 2 (for example a Unitree Go2's onboard stack).
2. **Deploys it.** The app ships through the normal `wendy run` pipeline: built
   locally, pushed to the device, and started detached under the app ID
   `sh.wendy.foxglovebridge`. Re-running the command first removes any previous
   instance, so it is always safe to run again.
3. **Forwards the port.** The bridge's WebSocket port (8765 inside the app) is
   forwarded directly over the LAN for `wendy device`, or through the Wendy
   Cloud tunnel broker for `wendy cloud device`. The CLI prints the
   `ws://localhost:<port>` URL to connect Foxglove Studio to. The cloud form pins
   both deployment and forwarding to the same selected asset.

```
Foxglove Studio --ws--> localhost:8765 --LAN/cloud--> foxglove_bridge (device) --DDS--> your ROS 2 apps
```

## Prerequisites

- The LAN form requires the selected device to be reachable on the local network.
  The cloud form requires cloud enrollment and a signed-in CLI session. See
  [Wendy Cloud](/docs/cloud).
- Docker on your development machine, so the CLI can build the bridge image.
- A ROS 2 stack producing topics on the device (your own apps, or a robot's
  native ROS 2 reachable over the host network).

## Flags

| Flag | Description |
| --- | --- |
| `--port` | Local port to forward the bridge's WebSocket to (default `8765`). |
| `--domain` | `ROS_DOMAIN_ID` the device's ROS 2 uses (default `0`). |
| `--rmw` | RMW implementation the device's ROS 2 uses (default `rmw_cyclonedds_cpp`). |
| `--distro` | ROS 2 distro the bridge image is built from (default `humble`). |
| `--interface` | Override the CycloneDDS network interface selected for a multi-interface device. |
| `--topic <regex>` | Replace the default topic set with a topic-name regular expression; repeat for multiple expressions. |
| `--all-topics` | Expose every topic, restoring the previous high-bandwidth behavior. |
| `--message-backlog <n>` | Maximum outgoing data messages queued per client (default `1`, so stale data is dropped instead of lagging). |

The global `--device` flag selects a device, as with every other command.

The default topic whitelist is:

```text
/tf
/tf_static
/front_camera/image/compressed
/odom
/joint_states
/diagnostics and /diagnostics/*
/uslam/frontend/odom
/sportmodestate and /lf/sportmodestate
```

Point clouds, raw images, and voxel, range, height, or cloud maps require explicit
opt-in because an active Foxglove panel can saturate a 100 Mbit robot link with
those streams. To choose a focused set, repeat `--topic`; custom expressions
replace the defaults:

```bash
wendy device foxglove serve \
  --topic '^/tf$' \
  --topic '^/tf_static$' \
  --topic '^/front_camera/image/compressed$' \
  --topic '^/uslam/frontend/odom$'
```

Use `--all-topics` only when the network can carry every topic needed by the
active Foxglove layout. ROS 2 domains are isolated graphs, so stop and restart
`serve` with a different `--domain` when you want to inspect another graph.

The bridge uses the device's host network for ROS 2 discovery, but its WebSocket
listener binds only to `127.0.0.1`. In Cloud mode it is reached through Wendy's
authenticated Cloud tunnel. With `wendy device`, traffic follows the already
selected LAN agent connection into the Foxglove app; the WebSocket is never
published on the device's LAN interfaces and the forward does not use Cloud.

<Callout type="warning">
**Match the bridge to your app's domain.** An app whose `frameworks.ros2` omits
`domainId` gets a stable auto-derived domain (a hash of its `appId`), not domain 0.
The bridge always uses an explicit domain (`--domain`, default 0), so for apps
using an auto-derived domain the bridge will not see their topics. The simplest
setup: set an explicit `domainId` in your app's `wendy.json` and pass the same
value with `--domain`.
</Callout>

For a robot whose ROS 2 runs on a non-default domain or middleware, match the
bridge to it:

```bash
wendy device foxglove serve --domain 42 --rmw rmw_cyclonedds_cpp
```

When no interface override is supplied, Wendy inspects the device's network
metadata. If exactly one interface has an address in Unitree's documented
`192.168.123.0/24` robot network, the command selects it automatically and adds
Unitree's public `unitree_go`, `unitree_api`, and `unitree_hg` message definitions
to the bridge image. This lets Foxglove decode core Go2 and G1 custom topics such
as `/lowstate`, `/sportmodestate`, `/lowcmd`, and `/armsdk`, and makes the normal
Unitree invocation simply:

```bash
wendy device foxglove serve --device Woof
```

The command reports the inferred interface before deployment. The subnet is a
strong signal that the device is Unitree-connected, but not proof of a specific
robot model. If detection is ambiguous or you need another network, override it
explicitly:

```bash
wendy device foxglove serve --domain 0 --interface enP8p1s0
```

Unitree-specific messages that are not part of the public `unitree_ros2`
repository are supplemented from a pinned official `unitree_sdk2` revision when
the SDK publishes their DDS definitions. Wendy generates the corresponding ROS
messages during the image build and rejects unknown SDK field types rather than
risk silently decoding an incompatible layout.

On a Go2, Wendy also requests JPEG frames from the native VideoHub service and
publishes them as `/front_camera/image/compressed`
(`sensor_msgs/msg/CompressedImage`). Select that topic in Foxglove's Image
panel. On Unitree models without the Go2 camera service, the adapter remains
idle without affecting the main Foxglove bridge.

Definitions absent from both public repositories (for example onboard-only
`unitree_interfaces` messages, `SymState`, and newer vendor-only service
definitions) remain unavailable unless their definitions are installed
separately.

Some Unitree firmware also advertises a single topic name with multiple
incompatible message types (for example `/lf/lowstate`). Foxglove cannot
disambiguate those publishers by topic name. Wendy leaves the topic visible
instead of silently choosing a type; the publishers must use distinct topic
names before both streams can be decoded reliably.

## Stopping and cleanup

Press **Ctrl-C** to stop the port forward. The bridge app keeps running detached
on the device. Run `serve` again at any time to redeploy and reconnect. To remove
the bridge from the device entirely:

```bash
wendy device apps remove sh.wendy.foxglovebridge --force --cleanup
```
